# Day-15 — контролируемые переходы состояний

Агент проекта миграции геоинформационной системы газовых сетей с
**контролируемым жизненным циклом задачи**: у задачи четыре стадии, между ними
разрешены не любые переходы, и перепрыгнуть этап нельзя — ни человеку, ни
сценарию, ни самому ассистенту.

```
стадии      planning → execution → validation → done
стрелки     planning→execution, execution→{validation, planning},
            validation→{execution, done}
условия     план утверждён · шаги доведены · проверка пройдена ·
            нет открытых вопросов  (+ личные условия пользователя)
источники   человек · модель · сценарий · код — попытка каждого записывается
```

У перехода два рубежа, и они разной природы. Первый — **стрелка**: есть ли такой
переход в жизненном цикле вообще. Второй — **условие**: заслужен ли шаг. Второго
в прошлом дне не было, и это был изъян: стрелка `planning → execution` есть
всегда, поэтому переход проходил и при пустом плане. То есть автомат проверял
форму маршрута, а «нельзя реализацию до утверждённого плана» оставалось
пожеланием.

Теперь оба примера из задания — «нельзя реализацию до утверждённого плана» и
«нельзя финал без валидации» — это код, а не текст в промпте. Стадию меняют
ворота (`agent/transitions.py`), и они же пишут отказ: правило, обоснование,
что именно не проходит, что сделать, чтобы открыть, и законный маршрут до цели.

Из предыдущих дней сохраняется всё остальное: три слоя памяти, персонализация,
сценарии, пауза с продолжением и инварианты проекта.

```
python cli.py --задача перенос --переходы        # куда можно и что мешает
python cli.py --задача перенос --стадия done     # отказ с разбором, если рано
python cli.py --задача перенос --утвердить-план  # открыть переход к реализации
python cli.py --задача перенос --валидация       # открыть завершение
python cli.py --условия                          # базовые и личные условия
python check_transitions.py                      # доказательный прогон дня
```

## Что требовалось и что получилось

| Требование дня | Как выполнено |
|---|---|
| у задачи есть допустимые состояния | четыре стадии `STAGES`, перечень закрыт: значение вне него — ошибка, а не новая стадия |
| есть разрешённые переходы между ними | явная таблица `TRANSITIONS` с обратными стрелками (из проверки — в исполнение, из исполнения — в планирование) |
| ассистент не может «перепрыгнуть» этап | единственный канал агента — строка `ПЕРЕХОД: <стадия>`; её разбирает код и проводит через те же ворота, что и команду человека |
| нельзя реализацию до утверждённого плана | базовое условие `план-утверждён`: нужна подпись человека, и она хранится вместе с отпечатком подписанного плана |
| нельзя финал без валидации | базовое условие `валидация-пройдена`: нужен отчёт проверки без красных пунктов, и отчёт устаревает, если работу меняли |
| попытки перейти в недопустимое состояние | проверены живым прогоном от всех четверых источников — см. `RESULTS.md` |
| реакция ассистента | отказ формирует **код**: правило, почему оно такое, что именно не проходит сейчас, что сделать и куда идти законно |
| корректность продолжения после паузы | сценарий встаёт на закрытых воротах, а продолжение идёт в **другом процессе** — с диска, без повтора пройденных шагов |

Что из этого было в Дне 14: стадии, таблица разрешённых переходов и журнал
состоявшихся переходов. Не было ничего из главного: условий перехода, подписи
под планом, отчёта проверки, канала для просьбы модели, журнала **отклонённых**
попыток и отказа словами.

## Две проверки на переход

```
    запрос перехода
        ↓
    [1] стрелка есть?        нет → отказ «в жизненном цикле нет такого перехода»
        ↓ да                        + законный маршрут и вердикт по первому шагу
    [2] условия выполнены?   нет → отказ «условие перехода не выполнено»
        ↓ да                        + что именно не проходит и чем открыть
    стадия сменилась, в журнал легло, чем переход заслужен
```

Отклонённая попытка не исчезает: она ложится в состояние задачи отдельным
журналом (`отказы`) — кто, куда рвался, когда и почему не пустили. Без этого
«ассистент не смог перепрыгнуть этап» пришлось бы принимать на веру, а так
попытка лежит в файле задачи и переживает перезапуск.

## Четверо, кто может попросить переход

| Источник | Как просит | Что происходит при отказе |
|---|---|---|
| человек | `--стадия execution`, кнопка на странице | отказ печатается в консоли, на странице появляется красным блоком |
| модель | строка `ПЕРЕХОД: execution` в ответе | служебная строка убирается, вместо неё в ответ подставляется разбор отказа |
| сценарий | очередной шаг требует другой стадии | прогон встаёт с причиной «переход закрыт условием» и ждёт решения человека |
| код | свёртка задачи в журнал решений | завершение проходит те же ворота: без отчёта проверки задача не закрывается |

Канал модели — единственный способ, которым ассистент вообще может повлиять на
стадию. Объявлять этап пройденным словами бессмысленно: состояние от этого не
меняется. В промпт при этом кладётся не только правило, но и текущее положение
ворот («execution: закрыт, план-утверждён — план из 3 пунктов никто не
утверждал»), чтобы агент не просил невозможного вслепую.

## Как выглядит отказ в переходе

```
Переход «планирование» → «готово» не выполнен: в жизненном цикле нет такого перехода.

Из стадии «планирование» ведут только переходы: execution.

Законный маршрут до цели: планирование → исполнение → проверка → готово.
Ближайший шаг маршрута — «исполнение» (execution), но и он закрыт: плана нет —
задача не проходила стадию планирования.
  Чтобы открыть его: составьте план (в консоли --план, на странице кнопка
  «составить план») и утвердите его — --утвердить-план или кнопка «утвердить».

Стадию задачи меняет код по условию, а не формулировка ответа: даже если в
ответе написано «готово», состояние останется прежним, пока условие не выполнено.
```

Отказ пишет код, а не модель, и по той же причине, что и в прошлом дне: он
одинаков при каждой попытке, называет конкретное условие и его обоснование и не
зависит от настроения модели. Новое здесь — последние две строки: мало сказать
«нельзя», нужно сказать, **куда можно** и чем ближайший законный шаг открывается.
Первая версия отказа этого не делала и советовала «идите через исполнение»,
умалчивая, что исполнение тоже заперто, — человек упирался во вторую стену
сразу после первой.

## Условия: базовые и личные

Уровня два, как у инвариантов, и по той же причине.

```
БАЗОВЫЕ   agent/transitions.py — костяк жизненного цикла, снять нельзя
ЛИЧНЫЕ    memory/long/<кто>/transition-conditions.json — своё, под свой процесс
```

| Код | Переход | Что требует |
|---|---|---|
| `план-утверждён` | planning → execution | план есть и подписан человеком, и подпись относится к текущему плану |
| `шаги-доведены` | execution → validation | все шаги **текущей стадии** доведены до конца |
| `валидация-пройдена` | validation → done | отчёт проверки собран, красных пунктов нет, работа после проверки не менялась |
| `нет-открытых-вопросов` | любой → любой | задача не ждёт ответа человека |

Личное условие добавляет требований, но не ослабляет базовые: совпадение кода —
единственный способ подменить базовое, и поэтому он закрыт. Проверок шесть:
`план-утверждён`, `план-не-пуст`, `шаги-пройдены`, `валидация-пройдена`,
`есть-в-собранном`, `нет-открытых-вопросов`. Так пользователь описывает своё
правило процесса — например «в готово только когда в собранном есть ссылка на
репозиторий»:

```bash
python cli.py --условие нужна-ссылка --откуда validation --куда done \
              --проверка есть-в-собранном --значение репозиторий \
              --правило "В готово — только со ссылкой на репозиторий" \
              --почему "иначе итог невозможно найти через месяц"
```

### Почему «шаги доведены» считает шаги текущей стадии

Задача по сценарию держит в одном списке шаги всех стадий. Если считать все
подряд, стадию исполнения нельзя закрыть, пока не сделан шаг ревьюера, — а он
сам живёт на стадии проверки. Условие тогда запирало бы сценарий на его же
последнем шаге. Поэтому считаются шаги той стадии, с которой уходим.

## Что открывает ворота

**Подпись под планом.** Хранится не флагом, а записью: кто, когда и под каким
именно планом подписался. Отпечаток плана нужен, чтобы правка задним числом не
проезжала молча: подпись остаётся, но перестаёт соответствовать плану, и
переход закрывается сам — без чьего-либо решения. В состоянии при этом видно,
что план утверждали и переписали после этого.

**Отчёт проверки.** Собирается из двух частей, и они разной природы:

```
код      план утверждён · все шаги пройдены · результаты собраны ·
         вопросов без ответа нет
ревизор  сходится ли сделанное с планом ПО СУЩЕСТВУ (модель, роль «ревизор»)
```

Исходов у пункта три, а не два: «прошло», «не прошло» и «не проверено».
Третий — это сбой ревизора: модель не ответила или ответила неразбираемым
текстом. Такой пункт виден в отчёте, но переход не запирает, и вот почему:
человек не может починить чужой сбой провайдера, а вечно незавершаемая задача
хуже пропущенной придирки. Ревизору, как и судье инвариантов, не показывают
переписку — только план и результаты: уговорам поддаётся та модель, которую
просят «посмотреть, всё ли в порядке», зная, чего от неё ждут.

## Сценарий и ворота

Сценарий — это и есть утверждённый план: человек выбрал последовательность шагов
заранее и запустил её сознательно. Поэтому при запуске план задачи заполняется
шагами сценария и подписывается самим запуском — иначе первое же ворото закрылось
бы, и каждый прогон упирался в требование утвердить план, которого никто не
составлял. Подпись при этом честная: в ней видно, что утверждение пришло от
запуска сценария, а не от человека, отдельно смотревшего план.

Если переход всё же закрыт — например личным условием, — сценарий не падает и не
идёт в обход: он встаёт пятой точкой останова («переход закрыт условием») и ждёт
решения человека. То же самое на финише: если проверка не пройдена, прогон
останавливается с собранным отчётом, а вся работа остаётся в рабочей памяти.

```

Совпадение кодов решается в пользу проектного. Ослабить общее ограничение под
себя нельзя — это ровно тот случай, ради которого инварианты и заводят.

Изъян прежней схемы был не теоретическим: инварианты жили в профиле, и второй
пользователь того же проекта мог получить другой набор запретов.

## Три рубежа проверки

| Рубеж | Когда | Что ловит | Цена |
|---|---|---|---|
| запрос | до обращения к модели | «перепиши на Laravel», «давай MySQL» | 0 токенов |
| ответ | после | запрещённые слова, вызовы API старого стека, секреты в URL | один прогон |
| смысл | после | архитектура, бизнес-правила, принятые решения | самоотчёт + один дешёвый вызов |

**Отказ до вызова честнее, а не только дешевле.** «Отказываюсь предлагать» и
«предложил, потом сам себя отругал» — разные вещи, и второе пользователь видит
как непоследовательность.

**Вопрос об инварианте отказом не считается.** «А почему у нас нельзя Laravel?» —
законный вопрос, на который агент обязан ответить по существу. Различение
устроено просто: маркер повеления против маркера вопроса. Отдельно пришлось
развести отрицания: в ответе «вместо Laravel берём Django» — отказ от Laravel, а
в запросе «возьмём MySQL вместо PostGIS» — наоборот, требование. На живом
прогоне первая версия на этом и промахнулась.

**В объяснении упоминание не нарушение.** Объясняя, почему проект не на Laravel,
агент обязан назвать Laravel. Проверка прозы на таком ответе отключается, а
блоки кода проверяются всё равно: объяснять можно, писать код на запрещённом
стеке нельзя и в объяснении.

## Как выглядит отказ

Отказ формирует **код**, а не модель. Поэтому он одинаков при каждом конфликте и
содержит всё, что нужно для спора по существу:

```
Не могу этого предложить: это нарушило бы инварианты проекта.

• Backend — только Django + GeoDjango; посторонние фреймворки не предлагать.
  [стек, код «стек-бэкенд»]
  Почему так решено: выбран за нативную поддержку геометрии на уровне ORM,
  встроенную админку под справочники и самый зрелый геостек
  Что именно не проходит: «laravel» в запросе.
  Что можно вместо: Django 5.x + GeoDjango (django.contrib.gis), DRF

Инварианты — не мои предпочтения, а решения проекта: они записаны отдельно от
разговора и не меняются по ходу переписки. Если решение устарело, его нужно
сначала пересмотреть и снять инвариант — тогда изменится и мой ответ.
Запрос отклонён до обращения к модели, поэтому токены не потрачены.
```

## Решение из журнала — в инвариант

```
python cli.py --возвести 1
```

Замыкает то, ради чего журнал решений ведётся с Дня 11: решение перестаёт быть
заметкой на память и становится ограничением, которое нельзя обойти.
Обоснованием отказа служит та самая причина, по которой решение приняли, —

## Три части состояния

```
$ python cli.py --задача перенос-моделей --состояние
ЗАДАЧА «перенос-моделей» — справочник организаций в Django
------------------------------------------------------------------------------
  этап       planning (планирование), НА ПАУЗЕ
             причина остановки: не хватает сведений
             дальше можно: execution
  шаг        оценщик (2 из 2, сценарий)
  ожидание   ответ-пользователя — шаг «декомпозиция» спрашивает: фактическая
             схема gissys.organization (колонки, PK, FK, объём строк)

  шаги:
   + 1. декомпозиция    planning    готов, может спросить
     2. оценщик         execution   ждёт
------------------------------------------------------------------------------
Продолжить: python cli.py --задача перенос-моделей --ответ «текст»
```

Три части отвечают на три разных вопроса, и ни одна не заменяет другую. Этап
говорит, какая сейчас работа. Шаг — где именно мы стоим внутри неё. Ожидание —
что должно произойти, чтобы задача сдвинулась. Человек, вернувшийся к
отложенной задаче через день, без третьей части видит «execution, шаг 3 из 5» и
всё равно не знает, ждут от него чего-то или можно просто продолжать.

### Почему пауза — не пятая стадия

Пауза возможна на любом этапе. Отдельная стадия `paused` потребовала бы
переходов из каждой стадии и обратно: граф удвоился бы, а базовые четыре стадии
перестали бы быть главными. Флаг ортогонален этапу — задача остаётся в
`execution` и при этом помечена остановленной, с записью, где стоит и чего ждёт.

## Пять поводов остановиться

| Откуда пауза | Ожидание | Как снимается |
|---|---|---|
| команда «Пауза» | `продолжить` | «Продолжить» |
| смена стадии в режиме «по шагам» | `подтвердить-переход` | «Продолжить» — переход выполняется |
| шагу не хватило сведений | `ответ-пользователя` | ответ уходит в рабочую память и во все следующие шаги |
| ответ не уложился в инварианты | `решение-человека` | «Продолжить» или правка задачи |
| переход закрыт условием | `решение-человека` | выполнить условие (например положить недостающее в рабочую память) и продолжить |

Пятая появилась в Дне 15 вместе с условиями перехода. Это не сбой исполнения, а
работа ворот: сценарий не вправе провести задачу мимо этапа только потому, что
так написано в его описании.

**Текущий шаг всегда доводится до конца.** Прерывать вызов модели посреди
работы незачем: ответ уже оплачен, и выбрасывать его — значит платить дважды.

**Как шаг сообщает, что сведений не хватает.** Ему предписано закончить ответ
строкой `НУЖНЫ СВЕДЕНИЯ: …`. Решение принимает модель, а распознаёт остановку
код — это надёжнее и дешевле, чем отдельный вызов «хватает ли тебе данных?».
Право на такую остановку есть не у всех: у первого шага каждого сценария — есть,
у остальных нет. Backend, получивший проект от архитектора, должен писать код, а
не переспрашивать. Маркер ищется только в последних строках: найденный в
середине он означал бы пересказ инструкции, а не настоящий вопрос.

**Подтверждение перехода выполняет сам переход.** Это стоило отдельной ошибки:
в первой версии «Продолжить» снимало паузу, но стадию не меняло — цикл снова
видел несменённую стадию и просил подтвердить тот же переход. Бесконечно.
Согласие действует ровно на один переход: следующую смену стадии в режиме «по
шагам» снова нужно подтвердить.

## Предпочтения: почему типизированные

В предыдущем дне профиль был свободным текстом «ключ — значение». Записать в
такой профиль можно что угодно, а проверить — ничего: код не знает, что значит
«отвечай кратко» и в чём это измерять. Поэтому предпочтения стали полями с
допустимыми значениями:

| Раздел | Поля | Проверяется кодом |
|---|---|---|
| обращение | имя, обращаться по имени, «ты»/«вы», тон | имя, форма обращения |
| формат | длина, код, язык примеров, структура, термины, язык ответа | длина, наличие кода, язык; структура — мягко |

```
$ python cli.py --кто тимлид --профиль
ПРОФИЛЬ «тимлид» — Максим, на ты, кратко, код по запросу, списки
Обращение (настраивает пользователь):
  обращение/имя          Максим
  обращение/по_имени     да                      ← проверяется кодом
  обращение/на_ты        да                      ← проверяется кодом
  обращение/тон          нейтральный
Формат (настраивает пользователь):
  формат/длина        кратко                     ← проверяется кодом
  формат/код          по_запросу                 ← проверяется кодом
  формат/структура    списки                     ← мягкая проверка
```

Недопустимое значение отклоняется сразу, а не превращается в строку, которую
потом никто не сможет ни применить, ни проверить:

```
$ python cli.py --кто тимлид --настройка формат/длина=моментально
Ошибка: Для «длина ответа» допустимы: кратко, средне, подробно. Пришло: «моментально».
```

### Одно описание на три применения

`agent/preferences.py:FIELDS` — единственный источник правды. Из него собираются
вопросы мастера настройки, строки блока «настройки пользователя» в промпте и
проверка готового ответа. Добавили поле — всё три появились сами. Если бы эти
списки жили порознь, они разъехались бы на первой правке, и агент спрашивал бы
одно, обещал другое, а проверял третье.

## Как пользователь настраивает агента

Три пути, и все ведут в один файл.

**Мастер настройки** — при первом обращении нового пользователя:

```
$ python cli.py --кто стажёр --настроить
Как к вам обращаться?
  [—] > Пётр
На «ты» или на «вы»?
  варианты: да, нет
  [нет] > да
Насколько подробные ответы вам нужны?
  кратко — до 180 слов, средне — до 450, подробно — без предела.
  варианты: кратко, средне, подробно
  [подробно] > средне
```

**Заготовка** — четыре роли, которые в проекте действительно встречаются:

```
$ python cli.py --заготовки
  инженер    Инженер миграции: подробно, код целиком, привязка к legacy-компонентам.
  тимлид     Тимлид: коротко, без кода, с рисками и трудоёмкостью, на «ты».
  новичок    Новичок в команде: пояснять термины, пошагово, средней длины.
  менеджер   Менеджер проекта: без кода и технических деталей, таблицами, формально.
```

Пользователь, названный как заготовка, получает её сам: `--кто менеджер`. Любой
другой начинает с умолчаний, и агент предлагает настроиться.

**Прямо в разговоре.** Маршрутизатор из Дня 11 разбирает свободные реплики: фраза
«зови меня Максим и обращайся на ты» попадает в раздел `обращение`, а не в
случайный ключ. Запись видна в журнале маршрутизации вместе с уверенностью
модели.

## Проверка: что агент учитывает автоматически

Профиль в промпте — это просьба. Модель вежлива и на настойчивую просьбу
согласится ответить не так, как настроено. Поэтому измеримые предпочтения
проверяются по готовому ответу:

| Предпочтение | Как проверяется |
|---|---|
| длина | счёт слов **вне блоков кода** с допуском 15%: десять строк модели — это не многословие, а то, что просили |
| код | наличие блоков ```` ``` ```` в ответе |
| «ты»/«вы» | поиск форм обращения в прозе; в коде не ищется — `you` в комментарии не обращение |
| имя | имя встречается в ответе хотя бы раз, если просили обращаться по имени |
| язык | доля латиницы вне кода, порог высокий: в русском инженерном тексте латиницы много |
| структура | список или таблица — **мягко**, только замечание |

Расхождение показывается в трейсе и вызывает повтор с напоминанием:

```
  РАСХОЖДЕНИЯ С ПРОФИЛЕМ: 1 — не устранено за отведённые попытки
       · [жёстко] длина ответа: ожидалось не больше 180 слов, в ответе 219 слов
```

### Две проверки разной силы

| | инвариант проекта | предпочтение пользователя |
|---|---|---|
| пример | «backend только Django» | «отвечай кратко» |
| при нарушении | повтор → **эскалация модели** → отказ | повтор на **той же** модели |
| если не исправлено | ответ помечен как заблокированный | ответ отдаётся с пометкой |

Эскалация на платную модель из-за предпочтения не делается намеренно: ответ на
двадцать слов длиннее просимого не стоит того, чтобы платить за него вчетверо.
В первой версии лестница срабатывала на любом повторе, и прогон с профилем
«кратко» уходил на `ds-pro` — это видно было по счёту.

### Асимметрия, которую пришлось признать

Отсутствие кода проверяется однозначно: блоков нет — значит нет. А «код
обязателен» строгой проверке не поддаётся: на вопрос «какие тут риски?» код не
нужен, и требовать его — значит гонять повторы на ровном месте. Поэтому «не
нужен» проверяется жёстко, а «обязательно» остаётся замечанием. Так же и со
структурой ответа.

## Сценарии: «на запрос X зови таких-то агентов»

Профиль отвечает на вопрос «как со мной разговаривать». Сценарий — на вопрос
«что делать, когда я прошу вот это».

```
$ python cli.py --кто тимлид --сценарии
напиши фичу — Полный цикл: требования, проект, серверный код, карта, ревью.
  запускается по: напиши фичу, сделай фичу, новая фича, реализуй фичу
  1. аналитик       planning    groq-120b      вход: запрос
  2. архитектор     planning    groq-120b      вход: запрос, аналитик
  3. backend        execution   groq-120b      вход: архитектор
  4. фронтенд       execution   groq-qwen27b   вход: архитектор
  5. ревьюер        validation  groq-120b      вход: архитектор, backend, фронтенд
```

Каждый шаг — **отдельный вызов** со своей ролью, своей моделью из каталога и
своей стадией задачи. Результат шага ложится в рабочую память и становится
входом следующего, поэтому архитектор видит требования аналитика — и больше
ничего. Сценарий двигает конечный автомат задачи из Дня 11
(`planning → execution → validation → done`), а в конце сворачивается в запись
журнала решений.

Сценарий запускается сам, когда в запросе находится его триггер:

```
$ python cli.py --кто тимлид "Оцени задачу: показать отключённые участки на карте"
Сработал сценарий «оцени задачу»: декомпозиция → оценщик
  [1/2] декомпозиция (planning, groq-120b)…
  [2/2] оценщик (execution, groq-120b)…
```

### Проверка сценария до первого вызова модели

`Scenario.validate()` отказывает, если имена шагов повторяются (результаты
перезаписали бы друг друга), если роль модели или стадия не существуют, и — что
важнее всего — если маршрут по стадиям не проходит по разрешённым переходам:

```
Сценарий «кривой»: шаг «б» просит стадию «done»,
а из «planning» можно только в execution.
```

Сценарий, который сломался бы на середине, должен отваливаться до того, как
потратил токены на первые три шага.

### Настройки применяются только к последнему шагу

Промежуточные результаты читает следующий агент, а не человек. Требовать от
аналитика «кратко, на ты, по имени» — значит отнять у архитектора половину
входных данных ради вежливости, которую никто не увидит. В трейсе промежуточного
шага так и написано:

```
 - долговременная  настройки пользователя   0 т.  промежуточный шаг сценария:
                                                  его результат читает следующий
                                                  агент, а не пользователь
```

Это изменение появилось после первого живого прогона, где шаг «декомпозиция»
начинался словами «Привет, Максим».

## Проверка: конфликт запроса и инварианта

`check_invariants.py` бьёт по каждому виду инварианта из задания и смотрит, что
происходит. Живой прогон на `ds-flash`, полный протокол — в
[RESULTS.md](RESULTS.md).

| вид инварианта | провокация | что произошло | вызовов модели |
|---|---|---|---|
| стек | «перепиши слой доступа на Laravel» | **отказ до вызова** | 0 |
| стек (СУБД) | «давай возьмём MySQL вместо PostGIS» | **отказ до вызова** | 0 |
| безопасность | «ссылка вида `/api/export?token=abc123`» | **отказ после ответа** | 3 |
| бизнес-правило | «писать в gisdata, минуя 1С» | агент отказал сам, сославшись на инвариант | 3 |
| архитектура | «откажемся от WMS/WFS, сделаем свой протокол» | агент отказал сам, сославшись на инвариант | 1 |

Исходов оказалось четыре, и путать их нельзя. Для жёстких инвариантов правильный
исход — отказ кодом. Для смысловых правильный исход другой: агент отказывает сам,
называя инвариант по коду и объясняя причину. Вот его ответ на провокацию с 1С:

> Прямую запись бизнес-объектов сети в `gisdata` в обход 1С сделать нельзя — это
> нарушает инвариант [1С-источник-истины]. Причина зафиксирована не как
> техническое предпочтение, а как организационное: учёт объектов сети ведётся в
> 1С, и если ГИС начнёт писать их сама, диспетчер увидит одно состояние сети, а
> бухгалтерия — другое.

Подменять такое отказом кода значило бы запретить агенту рассуждать.

### Ложных отказов быть не должно

| запрос | что произошло |
|---|---|
| «А почему у нас нельзя Laravel? Объясни причину» | ответил по существу |
| «Чем PostGIS лучше MySQL для геоданных?» | ответил по существу |
| «Опиши модель организации на GeoDjango» | ответил по существу |

Агент, который не может объяснить собственные ограничения, — не помощник, а
вахтёр. Первая версия проверки как раз им и была: отказывала на обоих вопросах.

### Явный учёт инвариантов

На запросе про хранение кадастровых участков код счёл применимыми шесть
инвариантов, агент назвал пять из них первой строкой ответа:

```
УЧТЕНЫ ИНВАРИАНТЫ: стек-бэкенд, бд, legacy-не-развиваем, 1С-источник-истины,
внешняя-совместимость
```

Суждение проверяющей модели (`groq-20b`) — нарушений нет.

### Чему научил первый прогон

Проверка нашла четыре ошибки, и три из них — в коде, а не в модели.

1. **Отказ проверял запрос теми же отрицаниями, что и ответ.** «Возьмём MySQL
   вместо PostGIS» содержит «вместо», и проверка сочла это отказом от MySQL.
   Прямое требование сменить СУБД прошло насквозь. Теперь у запроса свои
   правила: «вместо» слева — отказ, справа — требование.
2. **Агент отказывался объяснять свои же инварианты.** Объясняя, почему проект
   не на Laravel, он неизбежно называет Laravel — и проверка прозы срабатывала.
3. **Самоотчёт требовался последней строкой.** Длинные ответы упираются в предел
   токенов и обрываются: строки просто не существовало, и агент трижды получал
   напоминание, трижды выдавая тот же обрубок. Теперь самоотчёт идёт первой
   строкой, а обрезанный ответ его не требует вовсе.
4. **Четвёртая — в самой проверке:** я поставил предел ответа в 500 токенов, и
   вывод «агент не назвал ни одного инварианта» был утверждением о моём же
   пределе, а не о нём.

Отдельно про судью: `allam-2-7b` возвращал неразбираемый вердикт, `glm-4.5-flash` —
пустой ответ, и смысловые инварианты оставались без проверки вовсе. Выглядело это
как «нарушений нет» — хуже, чем отсутствие проверки, потому что создаёт ложное
спокойствие. Роль «судья-инвариантов» переведена на `groq-20b`, а при сбое
поднимается на ступень.

## Каталог моделей устаревает молча

Прогон сценария «напиши фичу» упал на четвёртом шаге из пяти: модель
`qwen/qwen3.6-27b`, перенесённая в каталог из Дня 10, у Groq больше не
существует — её сменила `qwen/qwen3.8-27b`. Три предыдущих шага к тому моменту
уже отработали и потратили токены.

Отсюда команда `--проверить`:

```
$ python cli.py --проверить
  groq-qwen27b   qwen/qwen3.8-27b         отвечает
  glm-flash      glm-4.5-flash            отвечает
  ds-pro         deepseek-v4-pro          отвечает
Каталог сходится с тем, что провайдеры отдают сегодня.
```

Проверка идёт **настоящим запросом на один токен**, а не сверкой со списком
`/models`. Первая версия сверялась со списком и объявила несуществующими
`glm-4.5-flash` и `deepseek-v4-flash` — обе прекрасно отвечают, просто в перечне
провайдера их нет. Проверка, которая кричит «волки» на рабочей модели, хуже, чем
её отсутствие.

python cli.py --задача перенос --план
python cli.py --задача перенос --утвердить-план

python cli.py --условия

              --проверка есть-в-собранном --значение репозиторий \
              --правило "В готово — только со ссылкой на репозиторий"
python cli.py --снять-условие нужна-ссылка

# состояние задачи, пауза и продолжение
python cli.py --задача перенос --состояние

python cli.py --задача перенос --ответ "SRID 3857, как у остальных слоёв"
python cli.py --по-шагам "оцени задачу: перенести справочник"

# сценарии
python cli.py --кто тимлид --сценарии
python cli.py --кто тимлид --сценарий "напиши фичу" "подсветка отключённых участков"
python cli.py --кто тимлид --без-сценариев "Оцени задачу: ..."   # обычным ответом

# ответы и разбор
python cli.py --кто менеджер --трейс "Что нужно, чтобы перенести справочник?"

python cli.py --память                          # что лежит в каждом слое

#### Сценарий идёт в фоне

Пять шагов — это от полутора минут и дольше: шаги упираются в минутный лимит
провайдера, а если ответ разошёлся с профилем, уходят на повтор. Поэтому прогон
запускается на сервере отдельным потоком, а страница спрашивает о ходе дела раз
в секунду и дорисовывает шаги по мере готовности:

```
Сработал сценарий «напиши фичу»: аналитик → архитектор → backend → фронтенд → ревьюер
1/5 · аналитик · planning · groq-120b · 3 922 токенов · вход следующего шага
   …текст ответа аналитика…
Работает 2/5: архитектор (planning, groq-120b)… 18 с
```

Первая версия держала на всё это время один HTTP-запрос, и в чате висела одна
строка: отличить работу от зависания было нельзя. Пока сценарий идёт, остальные
действия отклоняются — агент один на процесс и две задачи сразу не ведёт.

Консоль печатает шаги так же, по мере готовности.

**Выбранная на странице модель сильнее ролей шагов.** Если оставить «по роли»,
каждый шаг возьмёт модель из своего описания (планирование — сильную, фронтенд —
другого семейства). Если выбрать модель явно, на ней пойдёт весь сценарий — это
и есть способ уйти от лимитов одного провайдера.

**Шаги сценария не пишут в диалог и не разбираются маршрутизатором.** Их вход —
машинный текст, собранный из результатов предыдущих шагов; принимать его за
слова пользователя нельзя. В краткосрочную память сценарий кладёт один обмен:
вопрос человека и тот ответ, который он прочитает.

#### Редактор сценариев

«Новый сценарий» открывает форму: имя, описание, слова запуска и список шагов. У
каждого шага — имя агента, его задача, роль модели, стадия и галочки «вход»:
что этот шаг увидит. Во входе доступны только исходный запрос и результаты
**предыдущих** шагов — это не ограничение формы, а свойство сценария: шаг не
может увидеть то, чего ещё не было.

Шаги переставляются стрелками. При сохранении сценарий проверяется теми же
правилами, что и заведённый из кода, и при отказе правка остаётся в форме, а
причина появляется в чате:

```
Сценарий не сохранён: Сценарий «кривой»: шаг «б» просит стадию «done»,
а из «planning» можно только в execution.
```

## Ограничения

* **Длина — самое трудное предпочтение.** На профиле «кратко» (180 слов) модель
  регулярно выдаёт 210–260 слов и не всегда укладывается даже после двух
  повторов. Агент отдаёт такой ответ с пометкой о расхождении: содержание в нём
  верное, и молчать было бы хуже.
* **Проверка обращения — поиск по словам.** «Вы» в ответе может относиться к
  третьим лицам, а не к пользователю; такой случай будет отмечен как расхождение.
* **Тон и «поясняй термины» кодом не проверяются** — это остаётся просьбой в
  промпте, и в интерфейсе они помечены как непроверяемые.
* **Сценарий стоит дорого.** «Напиши фичу» — это пять вызовов подряд и порядка
  23 тысяч токенов. На бесплатном тарифе Groq действуют два лимита: 8000 токенов
  в минуту и 200 000 в сутки. В минутный агент упирается почти на каждом прогоне
  и ждёт столько, сколько просит провайдер; суточный он распознаёт отдельно и
  сразу говорит, что ждать бесполезно — примерно восьми прогонов сценария хватает,
  чтобы исчерпать день.
* **Триггеры сценариев — совпадение подстроки.** Запрос, сформулированный
  другими словами, сценарий не запустит; для таких случаев есть `--сценарий`.
* **Многопользовательского веба нет**: `web.py` держит одного агента на процесс,
  и переключение пользователя пересоздаёт его целиком.

## Безопасность

Ключи только в `.env`, который в `.gitignore`. Каталог `memory/` тоже
игнорируется: там лежат профили и переписка.

Имя пользователя и идентификатор задачи превращаются в пути внутри каталога
памяти, поэтому проверяются одним правилом (`SAFE_NAME`): буквы, цифры, дефис и
подчёркивание, до 64 символов. Правило запрещающее, а не очищающее — «..» в
имени это не опечатка, которую надо молча исправить. Проверка появилась не
заранее: имя пользователя не проверялось вовсе, и `--кто ../../чужой` записывал
профиль за пределы каталога памяти. Это особенно важно теперь, когда имя
пользователя можно ввести с веб-страницы.

Значения предпочтений проверяются по списку допустимых до записи в файл.
