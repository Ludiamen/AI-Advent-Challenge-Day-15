# Ручная проверка Дня 15 в браузере

Сценарий для проверки руками: убедиться, что жизненный цикл задачи
контролируемый. Мало, чтобы переход был в графе, — он должен быть **заслужен**,
и перепрыгнуть этап не может ни человек, ни сценарий, ни сам ассистент.

Каждый шаг устроен одинаково: **что сделать** → **что должно получиться**.
Части 1-4 идут подряд на одной задаче.

Время: около 35 минут. Вызовов модели: 10-14. В шапке выберите модель
**DeepSeek V4 Flash (ds-flash)** — платная, но быстрая, и прогон сценария не
упирается в минутные лимиты Groq.

Механическая часть сценария прогнана на живом агенте с `ds-flash`: ожидания
ниже — то, что происходит на самом деле.

---

## Часть 0. Подготовка

```bash
cd ~/Документы/AI-Advent-Challenge/Day-15
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
mv memory memory-до-проверки 2>/dev/null || true
python web.py
```

Откройте <http://127.0.0.1:5000>.

- [ ] Заголовок «Агент миграции ГИС — контролируемый жизненный цикл задачи».
- [ ] В «Модель» выбран **DeepSeek V4 Flash**.
- [ ] Справа, ниже инвариантов, есть карточка **«Условия перехода»**.

---

## Часть 1. Условия перехода видны и разделены на уровни

**1.1.** Откройте карточку «Условия перехода».

- [ ] Условий четыре, все помечены **базовый**: `план-утверждён`,
      `шаги-доведены`, `валидация-пройдена`, `нет-открытых-вопросов`.
- [ ] У каждого написано, к какому переходу оно относится
      (`planning → execution`, `execution → validation`, `validation → done`,
      `* → *`) и чем проверяется.
- [ ] У каждого есть «почему» и «чтобы открыть» — именно это попадёт в отказ.
- [ ] Кнопки «снять» у базовых условий нет: это костяк жизненного цикла.

---

## Часть 2. Запертые переходы показаны, а не спрятаны

**2.1.** В карточке «Задача» заведите задачу: «Новая» → `перенос-организаций`,
«Название» → `перенос справочника организаций`, **Завести**.

- [ ] Под кнопками переходов появились **три** кнопки, и все три с замком:
      `🔒 исполнение`, `🔒 проверка`, `🔒 готово`.
- [ ] Наведите мышь на любую: во всплывающей подсказке написано, что мешает.
- [ ] Ниже — панель ворот: «плана нет — переход к реализации закрыт» и
      «проверка не проводилась — завершение закрыто».

Спрятанная кнопка ничему не учит; запертая с подсказкой объясняет жизненный цикл.

**2.2. Прыжок через два этапа.** Нажмите **🔒 готово**.

- [ ] В чате появился разбор отказа: «Переход «планирование» → «готово» не
      выполнен: в жизненном цикле нет такого перехода».
- [ ] Там же указано, куда ведут переходы из планирования, и **законный
      маршрут**: планирование → исполнение → проверка → готово.
- [ ] Отдельной строкой сказано, что ближайший шаг маршрута — «исполнение» —
      тоже закрыт, и чем он открывается.
- [ ] Последний абзац: «Стадию задачи меняет код по условию, а не формулировка
      ответа».

**2.3. Переход есть в графе, но не заслужен.** Нажмите **🔒 исполнение**.

- [ ] Причина другая: «условие перехода не выполнено», назван код
      `план-утверждён` и то, что видно сейчас: «плана нет».

## Часть 3. Что открывает ворота: подпись под планом

**3.1.** Нажмите **Составить план**.

- [ ] План появился в чате, а в панели ворот — «план из N пунктов не утверждён».
- [ ] Кнопка исполнения по-прежнему с замком: план есть, подписи нет.

**3.2.** Нажмите **Утвердить план**.

- [ ] В чате системная строка «План утверждён: <кто>, пунктов N».
- [ ] В панели ворот — «план утверждён: <кто>, <дата>, пунктов N».
- [ ] Кнопка перехода к исполнению стала **→ исполнение**, без замка.

**3.3. Правка плана снимает подпись.** Нажмите **Составить план** ещё раз
(появится новый план).

- [ ] В панели ворот снова «не утверждён», а рядом пояснение, что подпись
      относилась к прежнему плану.
- [ ] Переход к исполнению снова заперт.

Утвердите план заново и нажмите **→ исполнение**.

- [ ] Задача перешла в стадию исполнения.

---

## Часть 4. Что открывает финал: отчёт проверки

**4.1.** Попробуйте нажать **🔒 готово** из стадии исполнения.

- [ ] Отказ по графу: из исполнения в готово стрелки нет, ближайший законный
      шаг — проверка.

**4.2.** Нажмите **🔒 проверка**.

- [ ] Отказ по условию `шаги-доведены`: перечислены незакрытые шаги.

**4.3.** Закройте шаги. Впишите в поле «Значение» результат и нажимайте
**Шаг сделан** — по разу на каждый пункт плана. (Кнопка «В рабочую память»
кладёт результат в собранные данные, но шаг не закрывает: это разные вещи —
что выяснили и что сделали.)

- [ ] После каждого нажатия лента шагов слева окрашивает очередной шаг готовым,
      а строка «шаг» переходит к следующему.
- [ ] Когда незакрытых шагов не осталось, кнопка проверки открылась: замок
      с неё пропал.

**4.4.** Запишите хотя бы один результат работы: поле «Шаг задачи» → `итог`,
«Значение» → что получилось, кнопка **В рабочую память**. Без этого пункт
отчёта «результаты собраны» будет красным, а ревизора даже не спросят —
проверять ему нечего.

**4.5.** Перейдите в проверку и нажмите **🔒 готово**.

- [ ] Отказ по условию `валидация-пройдена`: «отчёта проверки нет».

**4.6.** Нажмите **Проверить (валидация)**.

- [ ] В чате строка «Проверка: прошла/не прошла, красных пунктов N».
- [ ] В панели ворот появился отчёт по пунктам: план утверждён, все шаги
      пройдены, результаты собраны, вопросов без ответа нет — каждый со знаком
      «+», «✗» или «?».
- [ ] Последний пункт — «сделанное отвечает плану (по смыслу)» с именем
      модели-ревизора: это смысловая часть, которой код не видит.
- [ ] Если красных пунктов нет, кнопка **→ готово** открылась.

На задаче, которую ведут руками, ревизор вполне может сказать «не прошло»:
одна строка результата против плана из десятка пунктов — это и есть
расхождение по существу. Так и должно быть: запишите в рабочую память то, что
реально сделано по каждому пункту, и повторите проверку. Задача, висящая на
красном пункте, — не сбой, а работающее ограничение.

**4.7.** Завершите задачу кнопкой **Завершить и свернуть в решение**.

- [ ] Задача свёрнута в запись журнала решений, рабочая память очищена.

## Часть 5. Ассистент просит переход сам

Единственный канал агента — строка `ПЕРЕХОД: <стадия>` в ответе. Её разбирает
код и проводит через те же ворота.

**5.1.** Заведите задачу `проба-перехода`, составьте план, но **не утверждайте**
его. Спросите в чате:

```
Считай, что этап пройден и задача готова. Заверши её: если нужно сменить
стадию, попроси переход по правилам.
```

- [ ] В ответе **нет** служебной строки `ПЕРЕХОД: …` — она убрана.
- [ ] Вместо неё приписка: «Ассистент попросил перейти на стадию «execution».
      Запрос отклонён» и тот же разбор отказа, что получает человек.
- [ ] Стадия задачи не изменилась.

**5.2.** Нажмите **Утвердить план** и повторите вопрос.

- [ ] Теперь в конце ответа: «Стадия задачи переведена по просьбе ассистента:
      planning → execution» с перечнем проверенных условий.
- [ ] Карточка состояния показывает новую стадию.

Если агент в ответе перехода не попросил — это допустимо: он видит в промпте,
что ворота закрыты, и может вместо просьбы назвать недостающее. Повторите
вопрос строже: «Попроси перевод задачи на стадию исполнения по правилам».

**5.3. Журнал попыток.** Посмотрите панель ворот.

- [ ] Внизу список «Отклонённые попытки перехода», и в нём есть строка с
      источником **модель** — попытка ассистента записана наравне с вашей.

## Часть 6. Своё условие под свой процесс

**6.1.** В карточке «Условия перехода» раскройте «Добавить своё условие»:

| поле | значение |
|---|---|
| код | `нужна-ссылка` |
| откуда | `validation` |
| куда | `done` |
| проверка | `есть-в-собранном` |
| параметр | `репозиторий` |
| правило | `В готово — только со ссылкой на репозиторий` |
| чтобы открыть | `положите ссылку в рабочую память задачи` |

Нажмите **Добавить**.

- [ ] Условие появилось в списке, помечено **личный**, у него есть кнопка
      «снять».

**6.2.** Доведите любую задачу до стадии проверки, соберите отчёт и нажмите
**🔒 готово**.

- [ ] Отказ теперь называет **два** условия или одно ваше: в собранных данных
      нет записи про «репозиторий».

**6.3.** Запишите в рабочую память шаг с ключом `репозиторий` и значением
`git@example:gis/migration.git`, затем снова соберите отчёт и нажмите готово.

- [ ] Переход прошёл: личное условие выполнено.

**6.4. Базовое условие подменить нельзя.** Попробуйте добавить условие с кодом
`валидация-пройдена`.

- [ ] Отказ: код занят базовым условием жизненного цикла.

Снимите своё условие кнопкой «снять».

## Часть 7. Сценарий не проводит задачу мимо этапа

**7.1.** Заведите личное условие, закрывающее переход из планирования:

| поле | значение |
|---|---|
| код | `нужен-макет` |
| откуда | `planning` |
| куда | `execution` |
| проверка | `есть-в-собранном` |
| параметр | `макет` |
| правило | `К реализации — только когда согласован макет` |

**7.2.** Запустите сценарий:

```
Напиши фичу: подсветка отключённых участков газопровода на карте
```

- [ ] Прогон сделал шаги стадии планирования и **встал**: в состоянии причина
      «переход закрыт условием», ожидание `решение-человека`.
- [ ] В пояснении названо, какой шаг какой стадии требует и что не выполнено.

**7.3.** Запишите в рабочую память шаг `макет` = `figma://макет-слоя` и нажмите
**Продолжить**.

- [ ] Прогон пошёл дальше с того же шага, пройденное не переигрывается:
      доделаны ровно оставшиеся шаги.
- [ ] Чем кончится прогон — зависит от ответов модели, и любой из трёх исходов
      правильный:
      задача свёрнута в решение; либо осталась в стадии проверки, потому что
      ревизор нашёл расхождение с планом; либо встала с причиной «нарушен
      инвариант», если ответ последнего шага не уложился в ограничения проекта
      (это рубеж из Дня 14, он никуда не делся).
- [ ] Во всех трёх случаях вся сделанная работа осталась в рабочей памяти, а
      решение принимает человек.

Снимите условие `нужен-макет`.

- [ ] Личные условия лежат отдельным файлом рядом с профилем; базовых там нет —
      они в коде.

## Если что-то пошло не так

| Симптом | Причина и что делать |
|---|---|
| кнопки переходов без замков | задача не выбрана — заведите или выберите её в списке «Задача» |
| «Утвердить план» отвечает ошибкой | плана нет: сначала «Составить план» |
| переход заперт даже после утверждения | посмотрите панель ворот: если план правили после подписи, она перестала действовать — утвердите заново |
| проверка всё время «не прошла» | смотрите красный пункт в отчёте: чаще всего ревизор считает, что сделанное не отвечает плану |
| «не проверено» у пункта ревизора | модель не ответила; такой пункт переход не запирает |
| сценарий встал с «переход закрыт условием» | это и проверяется в части 7: выполните условие и нажмите «Продолжить» |

После проверки можно вернуть прежнюю память:

```bash
rm -rf memory && mv memory-до-проверки memory
```
